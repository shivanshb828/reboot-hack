# TriageDesk

**Hospital triage and on-call coordination — built on [Reboot](https://docs.reboot.dev).**

TriageDesk is a full-stack healthcare application that demonstrates three production-critical distributed systems guarantees that are unusually hard to get right: race-safe bed assignment under concurrent load, idempotent medication logging across retries, and crash-resilient on-call notification with exactly-once delivery semantics. It is also a voice-capable MCP application — a nurse can say *"book bed A1 for patient case 1042"* to Claude Desktop and the action completes with a live patient status card rendered inline.

---

## What it does

| Capability | Mechanism |
|---|---|
| Admit a patient to a bed | Distributed transaction spanning PatientCase + BedRegistry — two concurrent admits for the same bed can never both succeed |
| Log a drug administration | Writer with Reboot's gRPC-layer idempotency — retries never produce duplicate dose entries |
| Notify on-call staff | Durable workflow with `at_least_once_per_workflow` — survives a mid-execution server crash without double-paging |
| Live bed registry | Reactive Reader — shows every bed's assignment in real time across tabs |
| Voice-triggered admit via Claude | MCP tool suite + patient card HTML artifact — rendered inline in Claude Desktop |

## The three guarantees

### 1 — Race-safe bed assignment

Two nurses admitting different patients to the same bed at the same instant. Without a distributed lock, both reads see the bed as free and both writes succeed — one patient ends up physically in a bed with no record, the other has a record pointing to a bed occupied by someone else.

**How it works:** `admit()` is a `Transaction`. Inside the transaction it calls `BedRegistry.ref("global").reserve_bed(context, ...)`, enlisting that Writer in the same distributed commit. Reboot serialises all Writers on the same `BedRegistry("global")` state ID, so the second concurrent `reserve_bed` sees the first's committed result before it can write. If the bed is already taken, `reserve_bed` returns `bed_unavailable` and the transaction aborts before touching PatientCase state.

```
PatientCase.admit  (TransactionContext)
  └── BedRegistry.reserve_bed  (Writer, enlisted in same txn)
        ├── bed free?   → assign + return success
        └── bed taken?  → return bed_unavailable, txn aborts
```

**Proof:**
```bash
PYTHONPATH=backend/api:backend/src python backend/src/test_concurrent_admit.py
```

`asyncio.gather` fires two concurrent admits for the same bed from different patient cases. Expected output:

```
patient-alpha: success=False  message='bed_unavailable: bed 'bed-42' is assigned to 'patient-beta''
patient-beta:  success=True   message='admitted to bed 'bed-42''

✓  PASS: exactly one admit succeeded, one got bed_unavailable
✓  BedRegistry confirms bed 'bed-42' → 'patient-beta'
```

### 2 — Idempotent dose logging

A nurse logs a morphine dose; the network request times out and the client retries. Both requests arrive at the server. Without deduplication, `dose_log` gets the same entry appended twice — a phantom double-dose in the audit trail.

**How it works:** Reboot's gRPC middleware intercepts any RPC with an already-seen idempotency key and returns the cached response without invoking the Python method. The `dose_log.append()` line physically cannot execute twice for the same logical call — the interception happens before the servicer is entered. No application-level deduplication code exists in `log_dose`.

```python
async def log_dose(self, context: WriterContext, state, request):
    # Reboot's middleware has already filtered replays before reaching here.
    ts = datetime.now(timezone.utc).strftime("%Y-%m-%dT%H:%M:%SZ")
    state.dose_log.append(f"{ts}: {request.drug}")
    return PatientCase.LogDoseResponse()
```

### 3 — Crash-resilient on-call notification

The on-call pager fires successfully. A millisecond later the server process is killed. On restart, does the pager fire again?

**How it works:** `notify_oncall` is a Reboot `Workflow`. Inside the workflow, `at_least_once_per_workflow("send_page", context, _call_pager, type=str)` writes `mock_send_page`'s return value to RocksDB the moment the function returns. On restart, the workflow loop resumes; `at_least_once` finds `"send_page"` already in the RocksDB memoize store and returns the cached result without re-invoking `mock_send_page`. The subsequent `notify_status = "sent"` write then runs once and converges.

```
Loop iteration 1:
  read state → notify_status == "pending"
  at_least_once("send_page") → calls mock_send_page → stores result in RocksDB
  [SERVER KILLED HERE]

Restart, loop iteration 2:
  read state → notify_status still "pending"
  at_least_once("send_page") → finds stored result → returns immediately, NO CALL
  write notify_status = "sent"  ← converges
```

> **Honest caveat:** `at_least_once` guarantees no replay *after* `mock_send_page` returns. If the crash happens *during* the 1.5 s `asyncio.sleep` (before the function returns), the call is retried — that is the honest "at least once" contract. Real SMS APIs accept external idempotency keys that close this edge case.

**Proof:**
```bash
PYTHONPATH=api:backend/api:backend/src python backend/src/test_notify_workflow.py
```

Part 2 of the test monkey-patches `mock_send_page` with a barrier that signals after the function returns, calls `rbt.down()` in that window to simulate a crash, then `rbt.up()` to restart. Expected output:

```
✓  PASS: workflow converged after restart WITHOUT calling
   mock_send_page a second time — at_least_once memoization
   returned the stored result from RocksDB.
```

## Getting started

### Prerequisites

- Python 3.12+
- Node 18+
- [Reboot](https://pypi.org/project/reboot/) (`pip install reboot`)
- Envoy 1.38+ or Docker (for `rbt dev run`)

```bash
# Install Python dependencies
pip install reboot

# Install frontend dependencies
npm install --prefix=web --legacy-peer-deps
npm install --prefix=frontend --legacy-peer-deps
```

### Running locally

**Terminal 1 — Reboot backend + Envoy gateway**
```bash
export PATH="/opt/homebrew/bin:$PATH"   # ensure envoy is on PATH
rbt dev run
# Serves on :9991  (API + MCP + state inspector)
```

**Terminal 2 — React dashboard**
```bash
npm run dev --prefix=web
# http://localhost:3000
```

**Terminal 3 — Vite MCP UI** *(optional — only needed for MCP card in ext-apps hosts)*
```bash
npm run dev --prefix=frontend
# http://localhost:4444  (proxied via Envoy at /__/frontend/)
```

After any change to the API definition files in `api/`, regenerate stubs:
```bash
rbt generate
```

### Service URLs

| Service | URL |
|---|---|
| React dashboard | http://localhost:3000 |
| Reboot API gateway | http://localhost:9991 |
| MCP endpoint | http://localhost:9991/mcp/ |

## MCP — voice-triggered nurse workflow

TriageDesk exposes every state-machine method as an MCP tool. The full tool list:

| Tool | Description |
|---|---|
| `admit_patient` | Admit a patient to a bed (race-safe transaction) |
| `log_dose` | Log a drug administration |
| `notify_oncall` | Trigger the durable on-call notification workflow |
| `get_patient_status` | Get current patient case state |
| `get_patient_card` | Returns a self-contained HTML status card for artifact rendering |
| `check_bed` | Check whether a bed is currently assigned |
| `reserve_bed` / `release_bed` | Direct BedRegistry Writers (internal plumbing) |

### Connecting to Claude Desktop

**1. Expose the MCP endpoint publicly with ngrok:**
```bash
ngrok http 9991
# Copy the https URL, e.g. https://abc123.ngrok-free.app
```

**2. Edit `~/Library/Application Support/Claude/claude_desktop_config.json`:**
```json
{
  "mcpServers": {
    "triagedesk": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "https://abc123.ngrok-free.app/mcp/"]
    }
  }
}
```

**3. Fully quit and relaunch Claude Desktop** (`⌘Q`, not just close).

**4. Paste this system prompt in a new conversation:**
```
You are TriageDesk, a hospital triage assistant for nurses. When a nurse gives any command about a patient:
1. Call the relevant action tool (admit_patient, log_dose, notify_oncall).
2. Immediately call get_patient_card with the same patient_case_id.
3. Render the html_content field from the response as an HTML artifact — this is the patient's live status card.
Keep your text response to one sentence. The card is the UI.
```

**5. Say:** *"Book bed A1 for patient case 1042"*

Claude calls `admit_patient`, then `get_patient_card`, and renders the patient status card as an HTML artifact in the preview pane. After ~1.5 seconds, the on-call workflow completes and the `notify_status` badge flips from **pending** to **sent**. Say *"show me patient 1042's card again"* to see the updated state.

## API definition

The API is defined in pure Python (Pydantic) — `rbt generate` synthesises the proto, generates gRPC stubs, React hooks, and MCP tool bindings automatically.

```python
# api/triagedesk/v1/patient_case.py  (abbreviated)

api = API(
    PatientCase=Type(
        state=PatientCaseState,          # status, assigned_bed, dose_log, notify_status
        methods=Methods(
            get_status=Reader(...),
            get_patient_card=Reader(..., mcp=Tool(name="get_patient_card")),
            admit=Transaction(...,        mcp=Tool(name="admit_patient")),
            log_dose=Writer(...,          mcp=Tool(name="log_dose")),
            notify_oncall=Workflow(...,   mcp=Tool(name="notify_oncall")),
            patient_summary_card=UI(path="frontend/mcp/patient_summary_card"),
        ),
    )
)
```

Each `mcp=Tool(...)` annotation adds the method to the MCP server automatically. The `patient_case_id` parameter in every tool schema is injected by Reboot's MCP layer — it is not in the request model.
